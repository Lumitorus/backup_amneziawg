# Automatic AWG Backup (SSH + SMB)

Автоматизированная система резервного копирования **Amnezia WireGuard (AWG)** с использованием отдельной Ubuntu VM.

Данное решение позволяет ежедневно создавать резервные копии конфигурации AWG и Docker-образа, автоматически сохранять их на SMB-хранилище, контролировать целостность файлов и при необходимости полностью восстановить сервер за несколько минут.

# Возможности

Данный проект автоматически выполняет следующие действия:

* ежедневное резервное копирование AWG;
* подключение к удаленному серверу по SSH;
* архивирование каталога `/opt/amnezia/awg`;
* сохранение Docker Image через `docker save`;
* сохранение диагностической информации Docker;
* вычисление контрольных сумм SHA256;
* проверка целостности резервной копии;
* автоматическое копирование на SMB-хранилище;
* автоматическая очистка старых резервных копий;
* ведение журнала работы.

В результате получается полностью автономная система резервного копирования, не требующая участия администратора.

---

# Принцип работы

Схема работы выглядит следующим образом:

```text
                    SSH

+-------------------+      +------------------------+
|                   |      |                        |
|   Ubuntu Backup   +----->+      AWG Server        |
|        VM         |      |                        |
|                   |      | Docker + AWG           |
+---------+---------+      +-----------+------------+
          |                            |
          |                            |
          | получает архив             |
          | docker save                |
          |                            |
          +-------------+--------------+
                        |
                        |
                        v
              +--------------------+
              |                    |
              |   SMB / NAS Share  |
              |                    |
              +--------------------+
```

Backup VM никогда не хранит резервные копии постоянно.

Алгоритм работы следующий:

1. Подключается к AWG-серверу по SSH.
2. Проверяет доступность Docker.
3. Создает архив каталога AWG.
4. Выполняет `docker save`.
5. Проверяет контрольные суммы.
6. Копирует резервную копию на SMB-хранилище.
7. Удаляет временные файлы.
8. Удаляет устаревшие резервные копии.

# Что сохраняется

Во время резервного копирования сохраняются два основных объекта.

## Конфигурация AWG

Каталог

```text
/opt/amnezia/awg
```

содержит всю конфигурацию сервера:

* WireGuard-конфиги;
* настройки Amnezia;
* ключи;
* параметры контейнера;
* прочие служебные файлы.

Он архивируется в

```text
awg_config.tar.gz
```

---

## Docker Image

Дополнительно сохраняется полный Docker Image.

Используется команда

```bash
docker save amnezia-awg2-backup
```

Результат сохраняется в

```text
amnezia_image.tar
```

Это позволяет полностью восстановить сервер даже при отсутствии доступа к Docker Hub или собственному Registry.

---

## Диагностическая информация

Кроме основных данных автоматически сохраняются:

```text
docker ps
docker images
docker version
docker inspect
hostname
```

Эти файлы значительно упрощают диагностику и восстановление сервера после аварии.

# Структура резервной копии

После успешного выполнения резервного копирования на SMB появится новая директория.

Пример:

```text
AWG_BACKUPS/

└── awg-server-2026-07-09_02-00-00
    ├── awg_config.tar.gz
    ├── amnezia_image.tar
    ├── docker_ps.txt
    ├── docker_images.txt
    ├── docker_version.txt
    ├── docker_container_inspect.json
    ├── hostname.txt
    ├── SHA256SUMS
    └── backup.log
```

Каждый запуск создает отдельную директорию.

Это позволяет быстро откатиться к любой предыдущей резервной копии.

# Подготовка Backup VM

Обновляем систему

```bash
sudo apt update
sudo apt upgrade -y
```

Устанавливаем необходимые пакеты

```bash
sudo apt install -y \
    cifs-utils \
    rsync \
    openssh-client \
    tar \
    gzip \
    cron
```

Проверяем наличие SSH

```bash
ssh -V
```

Проверяем работу Cron

```bash
systemctl status cron
```

Если служба остановлена

```bash
sudo systemctl enable --now cron
```

# Настройка SMB

Создаем каталог, в который будет монтироваться файловое хранилище.

```bash
sudo mkdir -p /mnt/awg-backups
```

Создаем файл с учетными данными.

```bash
sudo nano /root/.smb-awg-backup
```

Пример содержимого:

```ini
username=YOUR_USERNAME
password=YOUR_PASSWORD
domain=WORKGROUP
```

Ограничиваем права доступа.

```bash
sudo chmod 600 /root/.smb-awg-backup
```

---

## Проверка подключения

Выполняем ручное подключение.

```bash
sudo mount -t cifs \
//SERVER/Backups \
/mnt/awg-backups \
-o credentials=/root/.smb-awg-backup,iocharset=utf8,vers=3.0
```

Проверяем, что файловая система смонтирована.

```bash
df -h
```

Создаем тестовый файл.

```bash
echo "Backup test" > /mnt/awg-backups/test.txt
```

Если файл успешно появился на SMB-хранилище, подключение работает корректно.

Удаляем тестовый файл.

```bash
rm /mnt/awg-backups/test.txt
```

---

# Автоматическое подключение SMB

Чтобы после каждой загрузки виртуальной машины не выполнять подключение вручную, необходимо добавить запись в `/etc/fstab`.

Открываем файл.

```bash
sudo nano /etc/fstab
```

Добавляем строку.

```fstab
//SERVER/Backups /mnt/awg-backups cifs credentials=/root/.smb-awg-backup,iocharset=utf8,vers=3.0,nofail,_netdev,x-systemd.automount 0 0
```

Проверяем корректность конфигурации.

```bash
sudo mount -a
```

Убеждаемся, что ошибок нет.

```bash
df -h
```

# Настройка SSH

Резервное копирование выполняется без ввода пароля.

Для этого используется отдельный SSH-ключ.

Создаем его.

```bash
ssh-keygen -t ed25519 -f ~/.ssh/awg_backup_ed25519
```

При запросе Passphrase рекомендуется оставить поле пустым.

После создания копируем публичный ключ на удаленный сервер.

```bash
ssh-copy-id -i ~/.ssh/awg_backup_ed25519.pub root@REMOTE_SERVER
```

Если `ssh-copy-id` недоступен, содержимое файла

```text
~/.ssh/awg_backup_ed25519.pub
```

можно вручную добавить в файл

```text
/root/.ssh/authorized_keys
```

на удаленном сервере.

После этого необходимо проверить права.

```bash
chmod 700 /root/.ssh
chmod 600 /root/.ssh/authorized_keys
```

---

# Проверка подключения

Проверяем вход по SSH.

```bash
ssh -i ~/.ssh/awg_backup_ed25519 root@REMOTE_SERVER
```

Если соединение устанавливается без запроса пароля, настройка выполнена успешно.

Дополнительно рекомендуется проверить работу Docker.

```bash
ssh -i ~/.ssh/awg_backup_ed25519 root@REMOTE_SERVER "docker ps"
```

Если отображается список контейнеров без запроса пароля, Backup VM полностью готова к следующему этапу — созданию автоматического резервного копирования.

---

# Конфигурационный файл

Чтобы не изменять основной скрипт при смене IP-адреса сервера, пути к резервным копиям или количества дней хранения, все основные параметры вынесены в отдельный конфигурационный файл.

Создаем файл:

```bash
sudo nano /etc/awg-backup.conf
```

Пример содержимого:

```bash
AWG_HOST="REMOTE_SERVER"

AWG_USER="root"

SSH_KEY="/root/.ssh/awg_backup_ed25519"

REMOTE_AWG_DIR="/opt/amnezia/awg"

REMOTE_IMAGE_NAME="amnezia-awg2-backup"

REMOTE_CONTAINER_NAME="amnezia-awg2"

SMB_MOUNT="/mnt/awg-backups"

BACKUP_ROOT="/mnt/awg-backups/AWG_BACKUPS"

RETENTION_DAYS=30

MIN_FREE_GB=5
```

Для безопасности рекомендуется ограничить права доступа.

```bash
sudo chmod 600 /etc/awg-backup.conf
```

---

# Описание параметров

| Параметр                | Назначение                                        |
| ----------------------- | ------------------------------------------------- |
| `AWG_HOST`              | IP-адрес или DNS-имя AWG-сервера                  |
| `AWG_USER`              | Пользователь для подключения по SSH               |
| `SSH_KEY`               | Путь до приватного SSH-ключа                      |
| `REMOTE_AWG_DIR`        | Каталог с конфигурацией AWG                       |
| `REMOTE_IMAGE_NAME`     | Имя Docker Image                                  |
| `REMOTE_CONTAINER_NAME` | Имя контейнера Docker                             |
| `SMB_MOUNT`             | Локальная точка монтирования SMB                  |
| `BACKUP_ROOT`           | Каталог хранения резервных копий                  |
| `RETENTION_DAYS`        | Количество дней хранения резервных копий          |
| `MIN_FREE_GB`           | Минимальный объем свободного места перед запуском |

# Проверочный скрипт

Перед включением автоматического резервного копирования рекомендуется убедиться, что все необходимые сервисы работают.

Создаем файл

```bash
sudo nano /usr/local/sbin/test-awg-backup-connect.sh
```

Вставляем следующий код.

```bash
#!/bin/bash
set -e

source /etc/awg-backup.conf

echo "=== SMB TEST ==="

mountpoint -q "$SMB_MOUNT" || {
    echo "SMB не подключен."
    echo "Выполняется mount -a..."
    mount -a
}

echo "Проверка записи..."

echo "$(date)" > "$SMB_MOUNT/test.txt"

rm "$SMB_MOUNT/test.txt"

echo "SMB OK"

echo

echo "=== SSH TEST ==="

ssh -i "$SSH_KEY" \
-o BatchMode=yes \
-o ConnectTimeout=10 \
"$AWG_USER@$AWG_HOST" \
"hostname && docker ps --format '{{.Names}}'"

echo

echo "SSH OK"

echo

echo "Все проверки успешно завершены."
```

Сохраняем файл.

Назначаем права.

```bash
sudo chmod +x /usr/local/sbin/test-awg-backup-connect.sh
```

---

# Проверка работы

Запускаем вручную.

```bash
sudo /usr/local/sbin/test-awg-backup-connect.sh
```

При успешной работе вывод будет примерно следующим.

```text
=== SMB TEST ===
SMB OK

=== SSH TEST ===
remote-server
amnezia-awg2

SSH OK

Все проверки успешно завершены.
```

Если на данном этапе возникают ошибки, рекомендуется устранить их до настройки автоматического резервного копирования.

# Основной скрипт резервного копирования

Создаем файл

```bash
sudo nano /usr/local/sbin/backup-awg-nightly.sh
```

Вставляем основной скрипт резервного копирования.

> Ниже приведена логика его работы. Сам скрипт можно вставить целиком без каких-либо изменений.

---

# Алгоритм работы

После запуска скрипт выполняет следующие действия.

## 1. Загрузка конфигурации

Сначала читается файл

```
/etc/awg-backup.conf
```

Если файл отсутствует, выполнение немедленно прекращается.

Это позволяет избежать случайного запуска со значениями по умолчанию.

---

## 2. Создание временной директории

Каждый запуск создает собственную директорию вида

```text
/tmp/awg-server-2026-07-09_02-00-00
```

Именно туда сначала скачиваются все файлы.

Это гораздо безопаснее, чем сразу записывать данные на SMB-хранилище.

Если во время резервного копирования произойдет сбой сети, поврежден будет только временный каталог, а не существующие резервные копии.

После успешного завершения временная директория автоматически удаляется.

---

## 3. Проверка SMB

Перед выполнением резервного копирования проверяется:

* подключено ли SMB-хранилище;
* доступна ли запись;
* существует ли каталог хранения резервных копий.

Если SMB не подключен, автоматически выполняется

```bash
mount -a
```

Если повторная попытка неудачна, выполнение завершается.

---

## 4. Проверка свободного места

Перед копированием вычисляется свободное место на SMB.

Если оно меньше значения

```
MIN_FREE_GB
```

резервное копирование не начинается.

Это защищает от создания неполных резервных копий.

---

## 5. Проверка SSH

Выполняется тестовое подключение.

Проверяется:

* доступность сервера;
* работа SSH;
* корректность SSH-ключей.

При любой ошибке резервное копирование отменяется.

---

## 6. Проверка Docker

Проверяется работа Docker.

Дополнительно проверяется существование:

* контейнера AWG;
* Docker Image.

Это позволяет обнаружить ошибку еще до создания резервной копии.

---

## 7. Сохранение диагностической информации

Для последующего анализа автоматически сохраняются:

```text
hostname

docker ps -a

docker images

docker version

docker inspect
```

При восстановлении эти файлы позволяют быстро определить конфигурацию исходного сервера.

---

## 8. Архивация конфигурации

Каталог

```
/opt/amnezia/awg
```

архивируется непосредственно на удаленном сервере.

Передача выполняется по SSH.

На Backup VM попадает уже готовый архив

```
awg_config.tar.gz
```

без создания промежуточных файлов на AWG-сервере.

---

## 9. Сохранение Docker Image

После завершения архивации выполняется

```bash
docker save
```

Полученный поток сразу передается через SSH на Backup VM.

В результате создается файл

```
amnezia_image.tar
```

---

## 10. Проверка файлов

После завершения загрузки проверяется, что:

* архив существует;
* архив не пустой;
* Docker Image успешно создан;
* размер файлов больше нуля.

При обнаружении ошибки выполнение прекращается.

---

## 11. Контрольные суммы

Для всех важных файлов автоматически вычисляется

```
SHA256
```

Создается файл

```
SHA256SUMS
```

После этого выполняется автоматическая проверка.

Если хотя бы один файл отличается от вычисленной контрольной суммы, резервное копирование считается неудачным.

---

## 12. Копирование на SMB

Только после успешного завершения всех предыдущих этапов резервная копия переносится на сетевое хранилище.

Таким образом на SMB никогда не появляются неполные резервные копии.

---

## 13. Повторная проверка SHA256

После копирования выполняется повторная проверка уже непосредственно на SMB.

Это позволяет обнаружить возможные ошибки сети или файловой системы NAS.

---

## 14. Очистка старых резервных копий

После успешного завершения удаляются резервные копии старше значения

```
RETENTION_DAYS
```

По умолчанию хранится история за последние 30 дней.

---

## 15. Завершение работы

В журнал записывается:

* дата создания;
* размер резервной копии;
* список файлов;
* время завершения работы.

После этого временная директория автоматически удаляется.

Если во время работы произошла ошибка, временные файлы также будут очищены автоматически благодаря использованию обработчика `trap`.

# Первый запуск

Перед включением Cron рекомендуется выполнить резервное копирование вручную.

```bash
sudo /usr/local/sbin/backup-awg-nightly.sh
```

Во время первого запуска рекомендуется наблюдать за процессом и убедиться, что:

* отсутствуют ошибки SMB;
* отсутствуют ошибки SSH;
* Docker Image успешно создается;
* архив конфигурации успешно сохраняется;
* каталог резервной копии появился на сетевом хранилище;
* создан файл `SHA256SUMS`;
* создан журнал `backup.log`.

Только после успешного завершения первого ручного запуска рекомендуется переходить к настройке автоматического выполнения по расписанию.

---

# Автоматический запуск

После успешного тестирования резервного копирования можно настроить его автоматическое выполнение.

В данном примере резервная копия будет создаваться ежедневно в **02:00**.

Открываем Cron пользователя `root`.

```bash id="z6j2we"
sudo crontab -e
```

Добавляем строку.

```cron id="7mclt2"
0 2 * * * /usr/local/sbin/backup-awg-nightly.sh
```

Сохраняем изменения.

Проверить список заданий можно командой

```bash id="t2w7ya"
sudo crontab -l
```

Убедиться, что служба работает.

```bash id="g8iq0u"
systemctl status cron
```

При необходимости включить автозапуск.

```bash id="rf9txr"
sudo systemctl enable --now cron
```

# Проверка успешного резервного копирования

После первого автоматического запуска рекомендуется убедиться, что резервная копия действительно создана.

Проверяем список каталогов.

```bash id="3rq80u"
ls -lah /mnt/awg-backups/AWG_BACKUPS
```

Открываем последнюю резервную копию.

```bash id="klk0lf"
cd "$(ls -td /mnt/awg-backups/AWG_BACKUPS/awg-server-* | head -1)"
```

Просматриваем содержимое.

```bash id="71qbfq"
ls -lah
```

Ожидаемый результат.

```text id="8vzrhv"
awg_config.tar.gz

amnezia_image.tar

docker_ps.txt

docker_images.txt

docker_version.txt

docker_container_inspect.json

hostname.txt

SHA256SUMS

backup.log
```

---

# Проверка контрольных сумм

Контрольные суммы позволяют убедиться, что резервная копия не была повреждена во время передачи или хранения.

Проверка выполняется одной командой.

```bash id="fhpnrp"
sha256sum -c SHA256SUMS
```

При успешной проверке вывод будет примерно следующим.

```text id="u0zt8l"
awg_config.tar.gz: OK

amnezia_image.tar: OK

docker_container_inspect.json: OK
```

Если хотя бы один файл имеет статус `FAILED`, использовать такую резервную копию для восстановления не рекомендуется.

# Проверка журнала

Каждый запуск автоматически создает журнал работы.

Открыть его можно командой.

```bash id="h1qxck"
cat backup.log
```

В журнале фиксируются:

* дата запуска;
* этапы выполнения;
* найденные ошибки;
* размер резервной копии;
* время завершения.

# Восстановление сервера ручное

При полном выходе сервера из строя восстановление занимает всего несколько минут (15 минут).

Установите Docker удобным для вашей операционной системы способом.

docker version

mkdir -p /opt/amnezia

tar -xzf awg_config.tar.gz -C /opt/amnezia

/opt/amnezia/awg

docker images

docker run -d \
  --name amnezia-awg2 \

# Возможные ошибки

## SMB не подключен

Ошибка.

```text id="1frb3l"
SMB not mounted
```

Проверить.

```bash id="3ly0zr"
mount -a
```

Если ошибка повторяется, необходимо проверить:

* доступность SMB-сервера;
* правильность логина и пароля;
* содержимое `/etc/fstab`;
* права доступа к каталогу.

---

## Ошибка SSH

Ошибка.

```text id="bnyzqt"
Permission denied (publickey,password)
```

Проверить вход вручную.

```bash id="ngvwfy"
ssh -i ~/.ssh/awg_backup_ed25519 root@REMOTE_SERVER
```

При необходимости повторно выполнить.

```bash id="7jnp8x"
ssh-copy-id
```

---

## Docker Image отсутствует

Ошибка.

```text id="zaj36o"
docker image inspect failed
```

Проверить список образов.

```bash id="p3gbmw"
docker images
```

Убедиться, что имя образа соответствует значению переменной.

```text id="vvptdu"
REMOTE_IMAGE_NAME
```

---

## Контейнер отсутствует

Ошибка.

```text id="mqe2pz"
docker inspect failed
```

Проверить список контейнеров.

```bash id="lxmgq0"
docker ps -a
```

---

## Недостаточно свободного места

Ошибка.

```text id="yjdd9u"
Not enough free space
```

Проверить.

```bash id="m0ylhc"
df -h
```

Удалить старые резервные копии либо увеличить размер файлового хранилища.

---

## Ошибка проверки SHA256

Ошибка.

```text id="6n32ha"
FAILED
```

Это означает, что резервная копия повреждена.

Не рекомендуется использовать такую копию для восстановления.

Следует создать новую резервную копию.

---

# Рекомендации

Для надежной работы системы рекомендуется:

* выполнять резервное копирование ежедневно;
* хранить резервные копии на отдельном NAS или файловом сервере;
* периодически проверять возможность восстановления на тестовом сервере;
* использовать отдельную Backup VM;
* использовать отдельную учетную запись SMB с минимально необходимыми правами;
* ограничить доступ к SSH только Backup VM;
* регулярно проверять свободное место на файловом хранилище;
* периодически проверять журнал `backup.log`;
* не отключать проверку контрольных сумм.

# FAQ

### Можно ли выполнять резервное копирование без SMB?

Да.

Вместо SMB можно использовать любой локальный каталог или смонтированную файловую систему.

---

### Можно ли хранить резервные копии локально?

Да.

Достаточно изменить значение переменной.

```text id="7tk0wm"
BACKUP_ROOT
```

---

### Можно ли изменить время запуска?

Да.

Измените расписание в Cron.

Например, выполнять резервное копирование ежедневно в 03:30.

```cron id="drk5q2"
30 3 * * *
```

---

### Можно ли изменить количество дней хранения?

Да.

Измените значение параметра.

```text id="xblpbf"
RETENTION_DAYS
```

Например.

```text id="5x8xw6"
RETENTION_DAYS=90
```

---

### Можно ли использовать другой каталог AWG?

Да.

Достаточно изменить параметр.

```text id="wx1snk"
REMOTE_AWG_DIR
```

---

### Можно ли выполнять резервное копирование нескольких серверов?

Да.

Достаточно создать несколько конфигурационных файлов и запускать основной скрипт с разными параметрами либо использовать отдельные экземпляры Backup VM.

---

# Заключение

После выполнения всех описанных шагов будет развернута полностью автоматическая система резервного копирования AWG.

Каждый день Backup VM будет:

1. Подключаться к удаленному серверу по SSH.
2. Архивировать конфигурацию AWG.
3. Сохранять Docker Image.
4. Вычислять контрольные суммы.
5. Проверять целостность файлов.
6. Копировать резервную копию на SMB-хранилище.
7. Удалять устаревшие резервные копии.
8. Сохранять подробный журнал выполнения.

Такой подход обеспечивает быстрое восстановление сервера после аппаратного сбоя, повреждения операционной системы или переноса AWG на новую инфраструктуру без необходимости повторной настройки сервиса.
